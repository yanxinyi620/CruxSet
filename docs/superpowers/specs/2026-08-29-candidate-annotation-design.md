# 候选标注交互设计

## 目标

将 Web 草稿编辑器的自动识别结果从“直接替换已标注岩点”改为独立候选层，保护用户已有手工标注，并提供逐个或批量确认、删除和类型修正能力。

## 范围

本阶段只修改 Web 草稿标注交互和前端状态管理，不改变 Layout 数据模型、服务端接口、发布规则或小程序端行为。自动识别算法继续使用阶段一实现；候选确认后仍通过现有 `LayoutEditor` 保存。

## 状态模型

草稿编辑上下文增加：

- `confirmed`: 现有已确认的 `Hold[]`，继续由 `LayoutEditor` 管理；
- `candidates`: 当前自动识别产生的 `Hold[]`，仅存在于当前会话；
- `candidateStatus`: `idle | detecting | ready`；
- `candidateNotice`: 候选数量、识别失败或无结果的提示。

再次自动识别只替换 `candidates`，不改变 `confirmed`。离开页面、刷新页面或保存草稿时，未确认候选不会写入 Layout。

## 交互设计

### 候选展示

- 已确认岩点沿用现有颜色；
- 候选使用半透明黄色边框和虚线，避免与已确认岩点混淆；
- 候选显示 `岩点/体积` 类型和数量；
- 候选与已确认区域重叠时仍可点击候选，确认前不改变已确认对象。

### 操作

- `确认全部`：将当前所有候选按原 ID 重新分配唯一 ID 后加入 `LayoutEditor`，然后清空候选层；
- `清空候选`：只清空候选层；
- 点击候选：选中候选并显示操作栏；
- `确认`：将单个候选加入已确认标注；
- `删除`：从候选层移除，不影响已确认标注；
- `转为岩点/体积`：修改候选类型后再确认；
- 候选可沿用现有移动和半径调整交互，但只有确认后才写入 `LayoutEditor`。

如果候选 ID 与已确认 ID 冲突，确认逻辑必须生成新的唯一 ID，不覆盖已有对象。候选确认顺序不影响最终 ID 唯一性。

## 数据流

```text
LayoutEditor confirmed holds
          │
          ├── 保存/发布 → 仅提交 confirmed holds
          │
自动识别 → candidates holds → 单个确认/全部确认 → LayoutEditor
                         └── 删除/清空/再次识别 → 仅影响 candidates
```

## 组件边界

1. `web/src/candidate-editor.ts`：纯候选状态转换函数，负责替换、确认、删除、类型修改和唯一 ID 分配。
2. `web/src/draft-canvas.ts`：增加候选渲染和候选命中回调，不直接修改 `LayoutEditor`。
3. `web/src/main.ts`：连接候选状态、工具栏操作、自动识别流程和保存/发布流程。
4. `web/src/styles/editor.css`：候选状态的控件和视觉样式。

## 错误处理

- 识别失败或无结果时保留既有确认标注和既有候选；
- 识别中禁止重复触发，但允许返回页面；
- 候选确认失败时不清空候选；
- 保存和发布只读取 `LayoutEditor.value()`，不会意外提交候选；
- 页面销毁后异步识别结果必须被忽略。

## 测试验收

- 生成候选不改变 confirmed；
- 再次识别只替换 candidates；
- 单个确认、全部确认后候选清空且 confirmed 增加；
- 删除和清空候选不改变 confirmed；
- 类型切换只影响候选；
- ID 冲突时生成唯一 ID；
- 保存/发布 payload 不包含未确认候选；
- 识别失败、无结果、重复触发和页面销毁场景均有测试；
- 运行全量测试、TypeScript 检查和 Web 构建。
